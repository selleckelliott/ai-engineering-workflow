# Project Adoption Protocol

Existing projects are not migrated automatically.

For each project, decide independently:

1. **Need** — What current planning, coordination, or handoff problem would this solve?
2. **Fit** — Should the project use local Markdown maps, GitHub Issues, or another tracker?
3. **Starting point** — Should the protocol begin with future work only, or should selected active work be mapped?
4. **Authority** — Which existing plans, tests, release gates, and operational documents remain authoritative?
5. **Concurrency** — How will ticket claims and parallel sessions be coordinated?
6. **Storage** — Which files belong in the product repository, and which remain in this shared repository?
7. **Rollout** — What is the smallest pilot effort that can validate the protocol without disrupting delivery?
8. **Exit** — How can the project stop using the protocol without losing important decisions or evidence?

## Default recommendation

Pilot the workflow on one new, bounded, multi-session effort. Do not retroactively map an entire mature backlog. Preserve existing release and testing authority until a deliberate project decision replaces it.
